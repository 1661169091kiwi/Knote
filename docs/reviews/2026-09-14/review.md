# Knote 性能诊断与侧边工具栏设计评审

日期：2026-09-14。检查基线：工作区当前 1.1.61，HEAD `c388baf`，包含用户尚未提交的 App.vue、AgentPanel.vue、agentStore.js 等修改。

本轮仅诊断和制作独立设计稿，没有修改应用源代码、安装应用、调用模型、改写用户文档或操作真实应用配置。下面的计时是本机 Node/ProseMirror 微基准，不是 Electron 全链路响应时间，也不是“已经解决卡顿”的声明。

## 结论

存在可以复现的异常开销，不能只归因于文档大或内存不足。最优先的是聊天缓存的容量断崖、代码块高亮的全量重算，以及 Mermaid 的集中绘制。标题相关优化确实已经部分生效，但还有全量遍历。

### 1. 长聊天缓存超过容量后反复全部失效——已复现

位置：`src/App.vue:8732–8743`，`src/components/AgentPanel.vue:1681–1729`。

当前每条助手消息都从模板调用 `renderAgentMd`。新增缓存是有效方向，但采用 `if (agentMdCache.size > 400) agentMdCache.clear()`。

从当前源码直接提取该缓存函数，以互不相同、内容保持不变的助手回复，按消息列表顺序连续访问三遍：

| 助手回复数量 | 第一遍实际渲染 | 第二遍实际渲染 | 第三遍实际渲染 |
| --- | ---: | ---: | ---: |
| 100 | 100 | 0 | 0 |
| 400 | 400 | 0 | 0 |
| 401 | 401 | 0 | 0 |
| 402 | 402 | 402 | 402 |
| 600 | 600 | 600 | 600 |

这里的 402 是隔离测试里的不同助手文本数量，不是总聊天条数的通用阈值。实际缓存还包含流式输出的不同前缀、尾部、语言/资源作用域，较短会话也可能在流式输出期间触发清空。

建议：历史消息用稳定消息 ID + 内容/图片资源版本保存渲染结果，流式尾部使用独立临时缓存；超出可视区域的历史消息再按内存预算回收。不能只把 400 调大，也不能只换成容量不变的 LRU——工作集大于容量、每轮又顺序扫遍全部消息时，依然可能持续失效。

### 2. 在一个代码块里输入，会重新高亮全部代码块——已复现

位置：`src/components/RichEditor.vue:608–610,2190`；实际安装依赖 `node_modules/@tiptap/extension-code-block-lowlight/src/lowlight-plugin.ts:47–65,104–145`。

当前继承的插件在编辑代码块时调用全篇 `getDecorations()`。此外，指定的语言不在已注册语法中时会调用 `highlightAuto`；当前注册 37 种语法，但没有 Mermaid，所以 Mermaid 源码也进入自动语言识别。

只读分析用户之前提供的 `OpenCode源码技术全景与架构解析.md`：

- 文件 586,237 字节、350,753 个 JS 字符；结构扫描统计 8,387 行、517 个标题、161 个 Mermaid 围栏。
- 当前策略确实切成 15 个富文本分片，最大一片 35,781 字符；不是全文仍一次性载入。
- 第一片 20,746 字符、39 个标题、13 个代码块，其中 12 个 Mermaid；最多的一片有 15 个 Mermaid 围栏。
- 使用第一片的真实代码块内容和实际安装的 ProseMirror 高亮插件，初次高亮调用：12 次自动识别 + 1 次指定语言，约 152 ms。
- 只向一个代码块插入一个字符：仍是 12 次自动识别 + 1 次指定语言，约 33 ms。

这些计时不包含真实编辑器 DOM、浏览器排版、Mermaid SVG 绘制。也不代表在普通段落打字一定触发全部高亮；该全量重算分支主要针对代码块编辑等变化。插件还会在事务中扫描新旧文档查找代码块，值得一并缩小范围。

建议：Mermaid/未知语言避免无意义的自动语言识别；仅对被修改的代码块重新高亮，其他 Decoration 使用位置映射保留。语言切换、跨块粘贴和整篇替换仍需正确失效，不能靠禁用所有高亮掩盖问题。

### 3. 分片中的 Mermaid 仍会集中启动绘制——源码确认，整机耗时待测

位置：`src/components/RichEditor.vue:686–716`、`src/lib/mermaidRender.js`。

每个 Mermaid NodeView 在创建时调用 `renderPreview(node)`，约 400 ms 后提交绘图，不检查是否在视口内；缓存仅记住当前 NodeView 的 `lastMmdSrc`，卸载/换片重建后不可复用。第一片的 12 个图会在接近的时间进入绘制流程。

建议：可视区域及少量预加载区域优先渲染；设置有限队列；按图源码、主题等渲染参数缓存结果；切片/关闭文档使陈旧任务失效。占位区域维持合理尺寸，避免渲染完成后跳动。这比继续把所有分片机械缩小更有针对性。

### 4. 标题问题不能一概而论——按钮复用有效，全量标记重建仍在

位置：`src/components/RichEditor.vue:1580–1705`。

本次更新已复用标题折叠按钮。在当前函数微基准中，连续 15 遍重建没有新增按钮，证实不是原来的每次输入都创建全部按钮。

但是每次 `tr.docChanged` 仍构造全部顶层节点数组、遍历标题、更新按钮属性、创建新的折叠 DecorationSet。用真实 ProseMirror 文档/Decoration、jsdom 按钮测试：

| 标题数量 | 热重建中位耗时 | 15 次重建新增按钮 |
| --- | ---: | ---: |
| 50 | 0.23 ms | 0 |
| 200 | 0.51 ms | 0 |
| 500 | 1.56 ms | 0 |
| 1,000 | 5.10 ms | 0 |

不包含浏览器布局，也不应用来直接推算实际输入延迟。尤其上述 OpenCode 第一片只有 39 个标题，不能把该文件的重卡顿直接归因于“全文有 517 个标题”。

建议：普通正文编辑只映射折叠位置/已有装饰；标题结构或折叠状态变化才更新相关区段。缓存按钮的点击位置必须同步，覆盖在标题前插入内容、重名标题、撤销和切片等边界。

### 5. 还有数个可缩小的工作范围——源码确认，尚未完整量化

- **移动光标也扫描全文**：`InlineRender` 对 `!tr.docChanged` 无条件 `scanWholeDoc()`，即使是无关元数据事务；建议无相关变化直接复用，只重扫旧/新光标所在块。`CalloutBlock` 的每次正文修改也全量扫描，可增量化。
- **聊天消息没有可视窗口限制**：整个 `chatMessages` 使用 `v-for` 挂载。缓存只减少 Markdown 解析，不减少全部消息的 VNode/DOM 数量。建议先拆分独立消息组件，再以动态高度窗口保留可视消息及缓冲；选择、复制、问句跳转、审核回执、切会话恢复必须保留。
- **问句定位仍线性读布局**：滚动回调每帧查询全部用户消息并读取 `offsetTop`。新代码的一次查询比逐条 querySelector 好，但可以缓存位置、局部修正、二分定位，避免随问句数增长。
- **一个超长代码围栏无法切流式尾部**：对 36,500 字符分段正文，当前切分函数留下 365 字符尾部；对 40,006 字符尚未闭合的代码围栏，尾部仍是全部 40,006 字符。建议对未完成的长代码块采用可追加的纯文本/延迟高亮显示，完成后一次格式化，不能强行在围栏内部拆成独立 Markdown 文档。
- **聊天持久化会做全记录序列化**：`persistChat` 经 `writeStoredChat` 同步 stringify/localStorage，随后持久化队列又 stringify/parse 深拷贝。需要测量大型会话保存峰值，再考虑变更记录写入、快照合并。不可为了性能取消持久化、删历史或弱化保存确认。

同时确认：统计/大纲目前已有延迟、可取消的分块分析，隐藏的整篇预览已有订阅条件，流式输出已有 80 ms 发布节流。侧栏 Agent 与浮窗 Agent 现在互斥；不要根据旧注释误报成“两套聊天同时展示”。关闭浮窗的 v-show 仍保留组件，应单独检查是否需要暂停界面工作，但不能停止用户允许的后台任务。

## 建议实施顺序及验收

1. 修聊天缓存断崖和代码高亮全量重算；这两项都有可重复的探针。
2. Mermaid 可视化调度/缓存；InlineRender 和标题装饰增量更新。
3. 聊天独立消息组件/长历史窗口、问句索引；保存峰值优化单独评估。

测试应覆盖 100/400/402/800 条不同回复、40k 字符长代码输出、密集标题、用户指定真实长文档的全部分片、输入法、持续打字/光标移动、切片后撤销、图片和修改审核。不仅测首次打开，还要测连续交互和返回旧会话；用本地录制流模拟 Agent，避免依赖线上模型或产生费用。

后续实施后，再在单个隔离配置的 Electron 实例中采集事务耗时、长任务和输入到绘制延迟，前后同样本比较；本轮没有这些全链路实测，因此不提供“已经流畅”的结论。完整大改后的验证/构建按 AGENTS.md 顺序执行。本轮纯诊断/设计，未运行完整 e2e 或制作安装包。

## 侧边工具栏设计——等待用户批准

预览：`sidebar-design.html`；截图：`sidebar-design.png`。

- 第一行：打开、保存、更多；保留文字，突出常用操作。
- 第二行：单栏/分栏为一个完整控件，语言和主题为较轻的次要操作。
